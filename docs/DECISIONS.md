# 设计决策

## D001：从可审查的 M0 / M1 小增量开始

依据上传需求中的开发顺序，先验证两层庇护所、三名角色、一处设施、自动到达和任务状态。当前没有把整个 MVP 一次性实现，也没有引入联网、账号、收费服务或生成式 NPC。

最初阶段验收重点：选人明确、点击派工、路线可见、等待有解释、能取消、不占用死锁。该阶段已交付；用户在 D009 中要求后续每轮提供更完整的可玩模块。

## D002：Godot 4.6.3 标准版、GDScript、Compatibility 渲染

采用需求文档建议的 Godot 4；环境已安装 4.6.3，实际用此版本导入和运行。标准版即可，兼容渲染适合这个轻量 2D 原型。不引入插件。优先面向 Windows 键鼠；当前测试宿主为 Linux，因此 Windows 真机验证和可执行文件导出仍待进行。

## D003：角色、任务规则、导航与显示分开

调度器是任务状态与设施占用的唯一管理者。角色管理自己的可视形象和移动，导航只返回路点，场景入口管理界面。采用普通对象和信号，不先创建通用组件框架、插件或大型全局管理层。

## D004：固定双层路点、先进先出、每人最多三项任务

一条楼梯让当前移动问题可被精确验证；后来增加通道时可以扩展连通图。按派工顺序等待，避免谁先走到谁就不断插队。重复任务完成后重新入队，防止某人独占设施。取消会清空此人全部任务，按钮和快捷键说明与这个规则保持一致。

这些均为原型规则，不锁定最终队列上限、角色数、任务时长或自动化方式。修整是调度演练，不产生或消耗生存资源。

## D007：M2 首个资源增量——灶台与共享库存

新增灶台并复用 `Workstation`；把单一等待队列改为每处设施各自的先进先出队列。角色的三项队列仍共用上限，可以混排不同任务。新增共享配方表和库存对象，不引入插件或服务。

配方是测试数值：生食 1 + 水 1 + 燃料 1 → 熟食 2，做饭 6 秒。初始 4 / 4 / 3 / 0。M02 交付时熟食只能累积；v0.3 已接入进食。没有无限生成物资的按钮、自动补料或资源自产。

## D008：开工扣料、取消退料、缺料跳过当前项

派工时检查材料，开工时再次原子校验并扣除。排队不占材料，因此用户看到的库存就是可用库存。当前采用易理解的取消策略：整锅退料、不产出熟食，完成后不能再退；以后若引入半成品 / 损耗，需要明确设计后另做增量。

开工缺料会失败当前项并继续下一项，而不是无限等待；新派工缺料直接拒绝。执行修整时追加做饭被拒绝，不得重置正在工作的进度。所有变化记录原因，库存不允许负数。

图形验收发现完成工作的人会停在交互点并遮住下一人，因而增加短暂的 `RETURNING` 状态：没有后续任务时自动让到个人等待位置；取消已开工任务也让位。它不占用设施，不新增任务，不消耗资源，新派工可以随时替换这段移动。

## D005：原创几何占位图与离线中文字体

用 Godot 绘图 API 表现房间、楼梯、人物、雨和灯光；不使用参考游戏的资产。字体取自 Noto Sans CJK SC，按当前界面字符子集化，以减少体积；随项目保留 OFL 许可。后续增加新中文文案时需要更新子集或改用完整字体，不能依赖目标电脑碰巧装有中文字体。

## D006：需求文档原样保留，工程状态另行记录

根目录需求文档保留上传原文，作为产品设计参考。实际做到了什么、未做到什么，以 `docs/PROGRESS.md` 和实际代码 / 测试为准。文档中的示例角色、游戏名、时间表及后期系统不当作已确定设计。

## D009：按用户新要求扩大每轮交付

用户明确要求“每次开发多一些完备一些”。从本轮起以完整的可玩模块组织增量，而非每轮只添一个任务；仍先说明设计、保持模块职责、运行真实检查并记录限制。

v0.3 交付“基地生活 + 持续存档”：五种任务、四处设施、需求消耗 / 预警 / 恢复、昼夜、健康与失败、保存 / 备份 / 恢复及完整控制界面。当时提前做了基地范围的存档；v0.4 的探索与兼容扩展见 D013—D016。

## D010：统一模拟时间与可预警的生存压力

1 倍速每秒两游戏分钟，完整一天 720 秒。饥饿、疲劳和生命都按模拟时间变化，暂停冻结、速度统一缩放。每次推进最大 1/60 秒子步，窗口卡顿不积累很长的强制离线消耗。

饥饿 / 疲劳先影响效率，达到更高阈值后缓慢损害健康；恢复任务不降速。死亡永久保留在存档，清除任务和占用，当前未完成用料不退。全员死亡才结束该局，没有天数强制结算。当前参数用于可玩验证，不锁定最终平衡。

## D011：前置任务资源预测，不预留、不自动消耗

允许为本人先排做饭再排吃饭，即使此刻没有熟食。只预测本人已有队列的可行产出，开工仍实际校验全部库存，前置失败时后续任务也可能失败并继续下一项。系统不自动给饥饿角色吃饭或消耗稀缺资源。

吃饭完成才恢复饥饿，防止“开吃 → 取消退料”无限恢复。睡眠按已休息时间恢复，中断保留收益且没有额外完成奖励。

## D012：单槽本地数据存档，先验证再恢复

v0.3 使用 schema 1 的 JSON 数据串和 SHA-256 损坏检测。全量验证数字、枚举、库存、路线、用料、队列、设施占用和完成次数后再应用。临时文件回读通过后才替换主档，保留上一有效主档为备份；未知更高版本拒绝，不猜测迁移。v0.4 增加明确的 v1→v2 迁移，保留这些读写约束。

手动 F6、每 60 模拟秒自动保存、正常关窗保存；启动恢复后暂停且不计算离线消耗。主档坏则尝试备份，两者都坏则停用自动保存。读档和新游戏都有确认，取消保留当前状态。保存失败的关窗也需用户确认后才丢弃进度退出。

JSON 解析的数值必须校验后转整数，不能拿浮点状态编号直接做枚举列表成员判断；浮点连续状态比较允许 1e-6 精度误差，离散状态和库存严格一致。详见 `docs/SAVES.md` 的实际故障与回归说明。

## D013：一次交付完整的实时往返

v0.4 同时实现出发准备、直接操控、两层地图、按住搜索、背包 / 丢弃、敌人感知 / 扑咬、挥击 / 急救、入口撤退、伤亡与基地治疗，接通“消耗 → 外出 → 带回物资与后果 → 恢复”的最小生存闭环。出门不会变成文字倒计时，搜到的东西也不会直接跨场景入库。

先做一个原创地点“河湾旧街”，六个容器、两层路线和可见敌人。限制空间规模，让撤退路径、搜索风险和持久化先可玩可验；多地点、跳跃、枪械、复杂视线、招募与正式美术仍留待后续完整模块。

## D014：一人外出，基地继续，统一时间固定 1x

出发者设为 AWAY 并退出基地派工与设施登记。探索坐标单独保存，健康直接更新原 Survivor，不创建一份需要合并的角色副本；两名留守者继续完成原队列。探索期间不能远程切人或派工，出门前安排具有实际作用。

同一模拟子步推进所有人需求、留守任务和探索，外出固定 1x；暂停冻结两边。准备窗口暂停，取消恢复原暂停状态；归来恢复原基地速度并暂停，给玩家检查后果的时间。模型与视图分别放在 `ExpeditionState` / `ExpeditionView`，视图不拥有另一套时钟。

## D015：有限装备、局部每日补给与可躲开的危险

工具按件消耗，一次成功破锁或击倒消耗一件；空挥不消耗，徒手只能推开。背包10格，携带装备也占空间，未使用物资归来返库。搜索必须到场并按住，超出容量的物资仍留容器。撤退必须亲自回入口，死亡丢包，不提供无风险传送。

敌人通过方向 / 距离、声音、掩体和警觉条行动，扑咬有0.8秒前摇，命中有短暂保护。没有按碰撞帧反复扣血。伤势与感染会延续到基地，药品是需要搜刮和安排治疗的有限资源。

同一天容器余量和已击倒敌人持久；新一天只在出发前补充两处轮换容器并公告敌人迁入，最多四名、生命固定40，不在活动地图突然生成。它解决首版补给来源和世界持久性，不代表最终无尽平衡或丰富事件内容已经完成。

## D016：扩展到 schema 2，但保留 v0.3 的真实进度

外出位置、背包、双方前摇、搜索 / 攀梯、容器与每日标记必须和基地一起验证恢复。文件路径保持不变，格式升到2。v1 的新字段按零值迁移，保留原队列、已扣材料和进度，不额外发药；升级保存保留原有效文件备份。

迁移样本来自归档 v0.3 程序实际运行，而非手工拼装。除单进程往返测试，还用三个独立 Godot 进程验证外出半程退出、正常恢复继续、归来再保存和再次启动，检查不二次扣装备、不重复入库、不重置容器。


## D017：回应用户的成品目标，提供可直接运行的桌面包

用户要求继续做成成品。本轮不把“完美”当作可凭空验收的事实，先交付三地点、真实维护 / 升级、事件 / 目标、游戏内指南 / 设置和Windows / Linux独立包。保留已能游玩的原循环，并验证状态连续性。

采用与引擎一致的官方4.6.3导出模板，嵌入游戏数据，发行包排除测试和开发文档，附Godot与字体许可。Linux实际启动与交互验证；Windows完成导出和格式检查，未做真机运行，不混称平台验证通过。

## D018：三个独立世界，不用换图刷物资

地点配置与玩家世界状态分开，根节点持有三份模拟模型。地图引用只在基地切换，其他地点保持余量与击倒状态；所有地点统一保存，各自验证几何和容量。地面长度、梯子、平台、掩体、巡逻、资源与配色各有差异，不只替换地点标题。

## D019：结构有代价，但不能锁死恢复

修整从免费练习改为开工消耗材料1、完成结构+18；取消不获益。结构影响生产速率，永不让工作台完全停用；恢复任务不受结构降速，避免低状态永久无法自救。三级升级降低磨损并提升生产，不制造食物 / 药品。

新配方不能让旧版免费练习凭空获得新材料或修复收益，因此迁移为进行中的旧修整添加显式标记，完成 / 取消按旧语义结束，队列下一项按新规则。真实v0.4样本同时覆盖外出和免费修整。

## D020：可预知天气、显式交易和非终局目标

天气在准备时公告，本趟保持不变；雨 / 雾影响可观察感知，贴身范围不隐藏。基地事件每次一个，保留到处理，费用与放弃后果先显示，缺料不扣部分资源，不能在外出时远程处理。

目标只展示里程碑，不发放无限补给或建立安全阶段。返库统计先减出发携带，装备往返不算探索。达到第七天或所有目标后仍可继续，符合无固定终局的方向。


## D021：独立运行必须验证真实系统窗口事件

源码内直接调用Node通知处理只能证明保存函数可用，不能证明系统关窗会到达它。独立程序探针发现了这条缺口，因此改成主Window的 `close_requested` 信号直接连接保存退出；退出按钮与进程探针也使用同一路径，另以真实X11关闭事件验证完整程序退出与恢复。

图形帧可能远快于音频混音缓冲；退出停止播放后按实际时间留120毫秒清理，避免用“两渲染帧”错误假定音频线程已释放播放对象。


## D022：完成长期平衡与人物系统

用户明确要求实现这两块。新增固定身份的有限成长、情绪 / 创伤、关系、共餐与医护援助、三个来访者、最多五位存活者和默认关闭的逐人照料授权。保留当局伤亡，角色成长最多15%加速，不用全能或无资源成本消除压力。

## D023：从真实多日运行发现并修补经济缺口

首轮14天策略可存活，但水容易囤积，徒手反复推搡会产生大量无风险重复控制。新增实际饮水需求、有限保鲜与明示损耗；推搡有疲劳成本，感染者失衡后有稳身期，不可续推。保留可观察前摇，允许通过准备和躲避保护药品，不人为强迫玩家受伤或偷偷删药。

三人与逐步五人策略从原库存连续推进14×720秒，通过真实探索获得物资；不探索和不照料的对照实际失败。报告记录参数、每日库存与策略边界，不用“时间跳到第14天”冒充长期验证。

## D024：用身份验证动态队伍，保留真实旧进度

保存schema4，前三位和三位固定来访者身份各不重复，最多6条历史 / 5位存活者，完整关系与伤亡账目一起验证。按已完成工作折算有限经验，不伪造探索经历，不额外送药或自动开启照料。旧敌人稳身补0，任务和地图进度原样保留。

实际归档程序生成schema3攀梯样本，加上已有schema1 / 2样本验证迁移；三进程另验证真实三天后招募的新成员外出、重启控制、回入口与再次保存，覆盖大于2的外出角色编号。

## D025 · 故事有两种完整选择，不抢暂停

八章手写事件根据实际人物、工作、归来、关系和伤亡触发；每章只出现一次，付费／保留物资都有独立结果。界面提前说明成本和情绪变化，缺料不部分扣款，阅读可以延后且无过期惩罚。谈话不补充物理需求，不发永久加成。

## D026 · 引导记录真实动作，不奖励点按钮

六个目标来自打开人物、真正进食／饮水／睡眠、净补给归来和维护据点。预排任务、空包或原装备往返不算，目标无固定顺序，可隐藏且可重看，进度随世界存档而非全局偏好保存。

## D027 · 长程用例保留完整记录，逆境夹具另列

正向用例从新局连续推进30／60天，不注入物资、生命、位置或经验。世界存档只保留最近30天，测试单独保留完整日记录；伤亡、重伤、药品清零和结构18%是另一个明确夹具，恢复阶段仅使用正常游戏操作。报告保留药品／材料积累的实际数据，避免把一条成功策略解释为所有资源均已平衡。

## D028 · 可选项目与互助消耗后期余量

三条路线、九个阶段，勘查需真实搜索并携净补给归来；建设需实际支付，日期／据点／照料条件提前说明。三种互助共用两日间隔，资源先完整扣除再得到补给，不能循环领取或外出远程兑换。保持可持续的食物／饮水需求，完成目标后继续生存。

## D029 · 普通版与验收版分别导出

普通包不包含自动控制，保留单文件内嵌数据。官方模板禁用--main-pack路径覆盖，验收使用独立入口场景和独立exe，配套Windows内置PowerShell及Linux系统输入工具。两者用相同游戏代码，均有SHA-256；验收槽位隔离正常存档。

## D030 · 冷启动关窗协议由虚拟显示工具初始化

Godot4.6.3只查询既有WM_DELETE_WINDOW原子。空白Xorg缺少窗口管理器时，验收工具需要在游戏启动前注册正常协议；重复测试先检查原子确实不存在，再正常关窗。窗口枚举抓取一致树并按PID查找，避免启动／销毁的临时窗口竞争。详见EXIT_DIAGNOSIS.md。
